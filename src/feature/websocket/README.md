# 1. 웹소켓의 개념

- 웹소켓은 단일 TCP 연결을 통해 전이중 통신 채널을 제공하는 통신 프로토콜이다. 클라이언트-서버 상호 작용을 위해 여러 번의 왕복이 필요한 반이중 방식인 HTTP와 같은 기존 웹 통신 프로토콜과 달리 웹소켓은 지속적인 요청 없이도 클라이언트와 서버 간의 실시간 양방향 통신을 가능하게 하여 지속적인 폴링(Polling)과 서버 전송 이벤트(Server Sent Events)와 같은 기술 없이도 데이터를 주고받을 수 있다.

### 폴링(Polling)

- 폴링은 클라이언트가 주기적으로 서버에 요청을 보내 새로운 응답이 있는지 확인하는 방식이다. 서버는 업데이트가 있으면 해당 정보를 응답하고, 그렇지 않으면 "없다"는 응답을 즉시 보낸다.

- 하지만 이 방식에는 두 가지 주요한 문제가 있다. 첫째, 요청 주기만큼 지연이 발생할 수 있다. 즉, 서버가 상태 변화를 즉시 반영할 수 없어 실시간으로 반응하는 데 한계가 있다. 둘째, 지속적으로 불필요한 요청이 서버로 보내지게 된다. 요청 주기가 짧을수록 반응 속도는 빨라지지만, 그만큼 트래픽 낭비가 심해지며 서버에 불필요한 부하를 줄 수 있다.

- 이 문제를 개선하기 위한 방법으로 Long Polling이 있다. Long Polling에서는 서버가 클라이언트의 요청에 바로 응답하지 않고, 데이터의 업데이트가 발생할 때까지 기다린다. 만약 업데이트가 발생하거나 설정된 타임아웃 시간이 지나면 서버는 응답을 보내고, 클라이언트는 다시 요청을 보내 다음 응답을 기다린다. 이 방식은 데이터 업데이트에 즉각적으로 반응할 수 있지만, 서버에 과도한 부담을 줄 수 있다. 여러 클라이언트가 동시에 연결을 유지하면 서버는 각 클라이언트와의 연결을 지속해야 하기 때문에, 서버의 부하가 증가하고, 결국 반응 속도가 느려질 수 있다.

## HTTP와 웹소켓 비교

### 1. HTTP 개념

- HTTP(Hypertext Transfer Profocol)는 클라이언트가 서버에 요청을 보내면 서버가 요청된 데이터로 응답하는 요청-응답 프로토콜이다. HTTP는 상태 비저장 방식으로 각 요청이 이전 요청과 독립적이며, 실시간 양방향 통신을 기본적으로 지원하지 않는다.

### 2. HTTP 특징

- **요청-응답 모델**: HTTP는 클라이언트가 요청을 시작하고 서버가 데이터로 응답하는 엄격한 요청-응답 모델을 따른다.

- **상태 비저장**: 클라이언트의 각 요청은 이전 요청과 독립적이며 서버는 클라이언트 상태를 유지하지 않는다.

- **무연결**: HTTP 연결은 수명이 짧으며 각 요청마다 새로운 연결을 설정헤야 한다.

- **단방향**: 통신을 클라이언트에서 서버로 한 방향으로만 이루어진다.

- **텍스트 기반 프로토콜**: HTTP 메시지는 사람이 읽을 수 있으며 헤더와 선택적 본문으로 구성된다.

### 3. 웹소켓 개념

- 웹소켓은 단일 TCP 연결을 통해 전이중 통신 채널을 제공하는 프로토콜이다. HTTP와 달리 웹소켓은 클라이언트와 서버 간의 실시간 양방향 통신을 지원한다. 채팅 애플리케이션, 공동 편집 도구 등 짧은 지연 시간과 높은 처리량이 필요한 애플리케이션을 위해 설계되었다.

### 4. 웹소켓 특징

- **전이중 통신**: 웹소켓은 클라이언트와 서버 간의 동시 양방향 통신을 허용한다.

- **영구 연결**: 한번 설정된 웹소켓은 연결 설정 및 유지와 관련된 오버헤드를 최소화하여 HTTP에 비해 지연 시간이 짧다.

- **짧은 지연 시간**: 웹소켓은 연결 설정 및 유지와 관련된 오버헤드를 최소화하여 HTTP에 비해 지연 시간이 짧다.

- **바이너리 및 텍스트 기반 데이터 교환**: 웹소켓은 바이너리 및 텍스트 기반 데이터 교환을 모두 지원한다.

- **프로토콜 업그레이드**: 웹소켓은 HTTP의 업그레이드 매커니즘을 따르기 때문에 두 프로토콜 간의 원활한 전환이 가능하다.

# 3. 웹소켓의 작동 방식

- 웹소켓은 클라이언트와 서버 간의 핸드셰이크 프로세스를 통해 설정되는 단일 TCP 연결 위에서 작동한다. 연결이 설정되면 클라이언트와 서버 모두 비동기적으로 서로에게 메시지를 보낼 수 있다. 이러한 양방향 통신을 통해 웹 애플리케이션에서 실시간 업데이트/스트리밍, 알림, 대화형 기능을 구현할 수 있다.

## 웹소켓 핸드셰이크

### 1. 웹소켓 핸드셰이크 개념

- 웹소켓 핸드셰이크는 클라이언트와 서버가 웹소켓 연결을 설정하는 프로세스이다. 여기예는 클라이언트에서 서버로 보내는 초기 HTTP 요청과 서버의 핸드셰이크 응답(서버의 응답도 HTTP로 보냄)이 포함된다. 이 핸드셰이크는 클라이언트와 서버 간의 전이중 통신을 허용하는 HTTP에서 웹소켓으로 연결을 업그레이드하는 데 필요하다.

### 2. 웹소켓 핸드셰이크 프로세스 단계

#### 1. 클라이언트 초기화

- 클라이언트는 'websocket' 값과 함계 'Upgrade'라는 특수 HTTP 헤더를 사용하여 서버에 웹소켓 핸드셰이크 요청을 보낸다.

- 이 요청에는 웹소켓 버전, 지원되는 하위 프로토콜 및 클라이언트가 랜덤으로 생성한 값을 Base64로 인코딩한 문자열(키)가 포함된다.

  <img width="100%" alt="클라이언트 요청에 담기는 헤더" src="https://github.com/user-attachments/assets/34808c37-ddbd-4aba-ac9e-8932c288bdc0">

#### 2. 서버 응답

- 서버가 핸드셰이크 요청을 수신하고 유효성을 검사한다.

- 서버는 요청을 받고 나서, GUID라 불리는 정해진 문자열을 그 키에 이어붙인 뒤 SHA-1 해시로 계산하여 다시 Base64로 인코딩한다.

  <img width="100%" alt="서버의 응답" src="https://github.com/user-attachments/assets/fcec298b-609d-43dc-b9c9-dcbd524fe4a0">

- 서버의 응답에는 웹소켓 버전, 선택한 하위 프로토콜(있는 경우), 클라이언트의 키, 고유 GUID 및 SHA-1 해시의 연결인 키가 헤더에 포함된다.

- 핸드셰이크 요청이 유효하면 서버는 웹소켓 프로토콜의 전환이 성공했음을 나타내는 101 상태 코드로 응답한다.

#### 3. 핸드셰이크 완료

- 클라이언트가 서버의 응답을 받으면 이것이 자기가 보낸 키로부터 생성된 값이 맞는지 확인하는 응답의 유효성을 검사한다.

- 응답이 유효하면 웹소켓 연결이 설정되고 이때부터 클라이언트와 서버는 HTTP가 아닌 웹소켓으로 통신한다.

# 4. 웹소켓의 장점

- **실시간 커뮤니케이션**: 웹소켓을 사용하면 클라이언트와 서버 간에 실시간 양방향 통신이 가능하므로 즉각적인 업데이트와 상호 작용이 가능하다.

- **효율성**: 기존 HTTP 요청과 달리 웹소켓은 여러 번 왕복할 필요가 없으므로 통신 효율이 높아진다.

- **짧은 지연 시간**: 웹소켓을 사용하면 메시지를 즉시 주고받을 수 있어 지연 시간이 짧은 상호 작용이 가능하다.

- **확장성**: 웹소켓은 많은 수의 동시 연결을 처리할 수 있어 높은 확장성이 필요한 애플리케이션에 적합하다.

# 5. 웹소켓의 단점

- **서버 설계의 복장성**: 특히 로드 밸런싱이 적용된 서버에서는 웹소켓 연결을 관리하는 데 추가적인 고려사항이 필요하다. 웹소켓은 특정 서버와 지속적인 연결을 유지해야 하므로, 한 서버와 연결이 시작되면 이후에도 계속 그 서버로만 데이터가 전송되도록 설정해야 한다. 이를 위해 NGINX와 같은 웹소켓을 처리할 수 있는 로드 밸런서를 설정하는 방법 등을 사용할 수 있다.

- **메시지 크기 제한**: 브라우저, 서버, 네트워크 환경에 따라 웹소켓에서 처리할 수 있는 메시지 크기가 제약될 수 있다. 대용량 데이터를 전송해야 할 경우, 데이터를 분할하여 전송하거나 다른 프로토콜을 사용하는 등의 방법을 고려해야 할 수 있다.

- **보안 문제**: 웹소켓의 기본 프로토콜인 WS는 암호화되지 않는다. 보안이 중요한 서비스에서는 SSL/TLS 인증서를 발급받고 이를 사용하여 WSS(WebSocket Secure)를 설정해야 한다.

- **서버 부하**: 웹소켓은 Polling 방식보다는 서버에 부담을 덜 주지만, 여전히 서버에 부하를 줄 수 있다. 많은 사용자가 동시에 접속하고, 메시지의 빈도가 높아지면 서버는 유지해야 하는 TCP 연결이 많아지고, 이에 따라 네트워크 대역폭과 CPU 사용량이 증가하게 된다. 따라서 웹소켓이 적합한지 여부는 구현하려는 서비스의 특성에 따라 신중히 고려해야 한다.

# 6. 웹 애플리케이션에서 웹소켓 구현하기

### 클라이언트

```javascript
// 새 웹소켓 연결 생성
const socket = new WebSocket('ws://localhost:8080');

// 웹소켓 연결
socket.onopen = (e) => {
  console.log('Connected to WebSocket server!');
};

// 수신 메시지 처리
socket.onmessage = (e) => {
  console.log('Received message:', e.data);
};

// 서버에 메시지 발송
socket.send('Hello, server!');
```

### 서버(Node.js)

```javascript
const WebSocket = require('ws');

const wss = new WebSocket.Server({ port: 8080 });

wss.on('connection', (ws) => {
  console.log('Client connected');

  ws.on('message', (message) => {
    console.log('Received message:', message);
    ws.send('Hello, client!');
  });
});
```
